# GitButler local use and team compatibility

Date: 2026-11-10. Scope: GitButler's current documentation and public source; this answers whether one person can use it in a team that continues using ordinary Git.

## Answer

**Yes, for the Git workflow: you can use GitButler locally while teammates continue using Git, without requiring them to install GitButler or create GitButler accounts.** GitButler operates on normal Git repositories and describes itself as a Git-backed client / new porcelain; its output works with nearly all Git commands. Your commits and branches remain local until you push them to the team's ordinary Git remote. The team can then review, fetch, merge, and continue working through its existing Git host and tools. [Getting started](https://docs.gitbutler.com/guide), [Starting in a Repository](https://docs.gitbutler.com/cli-guides/cli-tutorial/initializing-a-repository), [GitButler source README](https://github.com/gitbutlerapp/gitbutler#gitbutler)

**But “completely locally” is not literally “offline / no network.”** GitButler can work against a local repository without connecting a forge, but fetching and pushing use a remote, optional forge integrations call the forge APIs, and the checked-in default settings enable anonymous metrics and anonymous error reporting. [Push and fetch](https://docs.gitbutler.com/features/branch-management/pushing-and-fetching), [GitHub integration](https://docs.gitbutler.com/features/forge-integration/github-integration), [default settings](https://github.com/gitbutlerapp/gitbutler/blob/master/crates/but-settings/assets/defaults.jsonc)

## What is local, and what is shared

- **Local workflow:** Import an existing local Git repository and make commits/branches with GitButler; the getting-started guide presents GitButler-account login and GitHub connection as optional. With one branch applied, the repository remains a normal checkout. With multiple branches applied, GitButler uses a `gitbutler/workspace` checkout to represent them together. [Guide](https://docs.gitbutler.com/guide), [repository initialization](https://docs.gitbutler.com/cli-guides/cli-tutorial/initializing-a-repository)
- **Git compatibility:** GitButler works on ordinary Git repositories, not a separate hosted VCS. Its docs say nearly all Git commands work with what it produces. There is one practical caveat: while using multiple applied/virtual branches, stock Git commands involving the index, `HEAD`, commits, or branch switching may behave unexpectedly; use GitButler's workflow in that same working directory, or tear down to one branch. This does not require teammates in their own clones to use GitButler. [Repository initialization](https://docs.gitbutler.com/cli-guides/cli-tutorial/initializing-a-repository), [Desktop overview](https://docs.gitbutler.com/overview)
- **Sharing:** Commits are local until pushed. To share work, push a branch to a remote the team already uses; GitButler uses the system Git executable and its SSH config, SSH agent, or credential helper. No GitButler-hosted repository is required by these Git push/fetch docs. [Push and fetch](https://docs.gitbutler.com/features/branch-management/pushing-and-fetching)
- **Forge-specific collaboration:** Creating or managing PRs/MRs from inside GitButler requires authenticating a forge account (GitHub, GitLab, or Bitbucket). The normal Git remote workflow does not: GitButler can push branches without a forge integration, and its direct-land workflow works without one. Teammates can still use the hosting provider's normal review UI. [Forge tutorial](https://docs.gitbutler.com/cli-guides/cli-tutorial/forges), [Push and fetch](https://docs.gitbutler.com/features/branch-management/pushing-and-fetching)
- **GitButler account and AI:** The desktop onboarding guide explicitly says logging in to a GitButler account is optional, while noting it enables AI features such as commit-message generation. Current CLI docs also document configuring external AI providers or local Ollama, so AI is a separate opt-in path, not a prerequisite for ordinary local Git work. [Guide](https://docs.gitbutler.com/guide), [`but config`](https://docs.gitbutler.com/commands/but-config)

## Network, telemetry, and license caveats

- The public default-settings file currently sets `telemetry.appMetricsEnabled` and `telemetry.appErrorReportingEnabled` to `true`, describing them as anonymous metrics and anonymous error reporting. CLI documentation provides `but config metrics disable` to turn metrics off and points to GitButler's [privacy policy](https://gitbutler.com/privacy). This is a concrete caveat to “all local”; it is not evidence that source code or commits are uploaded as telemetry. [Default settings](https://github.com/gitbutlerapp/gitbutler/blob/master/crates/but-settings/assets/defaults.jsonc), [`but config metrics`](https://docs.gitbutler.com/commands/but-config)
- The checked defaults also configure periodic auto-fetch (15 minutes) and application update checks (3,600 seconds). Those make network activity possible when a remote/update service is configured/reachable. They are settings, not a requirement to host code with GitButler. [Default settings](https://github.com/gitbutlerapp/gitbutler/blob/master/crates/but-settings/assets/defaults.jsonc)
- GitButler's source is public, but the project license is **FSL-1.1-MIT** (Fair Source, not conventional OSI-approved open source): it permits internal use and other listed permitted purposes, prohibits competing uses, and grants an MIT license two years after each software version is made available. This matters if evaluating source modification or redistribution, not for teammates using ordinary Git. [License](https://github.com/gitbutlerapp/gitbutler/blob/master/LICENSE.md), [README license summary](https://github.com/gitbutlerapp/gitbutler#license)

## Practical setup

Keep the existing remote and review process. Use GitButler for your local branch/commit workflow, push the resulting branch to the same remote, and let teammates handle the branch with Git and their usual forge UI. No team-wide migration is implied. If the requirement is strict network isolation, separately disable/check telemetry, update checks, and remote fetching; the available docs do not establish that the stock app has a single “zero network” mode.

## Verification and limits

- Sources checked on 2026-11-10: official GitButler docs, GitButler's public source repository, and the current repository's existing research-note convention.
- The settings source URL tracks `master`, not a release tag; defaults could change between app versions. The settings file establishes configured defaults, not a packet-level audit of what telemetry contains or when it is sent. No app build, network capture, or runtime test was performed.
- “No GitButler account required” is scoped to local Git operations and pushing through system Git credentials; GitButler-hosted/forge/AI features may have their own authentication or provider requirements.
